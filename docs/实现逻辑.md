# Method 实现逻辑

这份文档写每个模块管什么、状态从哪里来、两层校验各拦什么、计划落到哪。

- 插件不自己存状态：状态全部从会话日志折叠得出。
- 计划的结构由两道关拦：参数 schema 挡形状，内容校验器挡语义。
- 计划落盘到项目根下的 `.method/plan.md`，同目录自带 `.gitignore`。

## 模块划分

| 文件 | 管什么 |
| --- | --- |
| index.js | 装配入口：注册投影、提示词段落、`/method` 命令、`plan_submit` 工具、参数形状校验、计划落盘 |
| state.js | 状态字段与折叠、计划路径解析、计划目录创建、参数 JSON 容错解析 |
| validate.js | 计划内容校验：目标与非目标、约束、方案比较、任务与依赖图、验证覆盖、元信息；渲染成模型可见的文本 |
| methodology.js | 注入文本：方法协议段落、工具描述、进出模式的两条提示 |

- 依赖方向单向：index.js 依赖其余三个，其余三个互不依赖。
- 被依赖的三个模块都是纯函数或纯数据，`node selftest.mjs` 直接测它们，不需要宿主。

## 状态模型

一个会话五样状态：

| 状态 | 含义 |
| --- | --- |
| 已提交的启用状态 | 布尔；这个会话算不算在模式里 |
| 正在执行的那次选择 | 当前这条进入命令要把它切成什么；没有正在执行的命令就是空 |
| 待提交的调用记录 | 调用标识到入参字符串的映射；每个 `plan_submit` 调用一条，结果回来后删掉 |
| 最近一次被接受的计划 | 已提交的计划对象；没提交过就是空 |
| 修订号 | 已接受的计划数，从零开始 |

- 注册为会话投影单元，只有宿主半边：不声明客户端可见的视图。
- 状态是纯 JSON，**且必须是纯 JSON**：投影缓存用 `snapshotJsonValue` 落盘，遇到 `Map`、`Set`、`undefined` 一律拒绝整行。待提交记录因此是普通对象，不是 `Map`。
- 折叠函数对无关事件必须返回同一个状态引用，投影按引用相等判断有没有下游工作。
- 注册键 `method`，状态版本 1；改状态字段或折叠语义时版本号加一，否则持久化缓存里的旧行会被前向折叠成垃圾。

### 折叠规则

| 会话日志里出现 | 折叠结果 |
| --- | --- |
| 进入命令开始（`command/run`，名字是 `method`） | 记下这次选择：参数去空格后等于 `off` 是想关，否则想开 |
| 进入命令结束（`command/done`，标识对得上） | 成功就提交为新状态，失败就丢弃；两种都清掉这次选择 |
| 进入命令结束，标识对不上，或没有正在执行的选择 | 状态不动 |
| `plan_submit` 被调用（`tool/call`） | 按调用标识记下这次的入参字符串 |
| 这次调用的结果回来（`tool/result`，标识对得上） | 结果带错误标记：删掉这条记录、计划与修订号不动；否则解析这条记录的入参，提交为最新计划、修订号加一 |
| 结果回来但标识对不上 | 状态不动，那条记录继续等自己的结果 |
| 其它任何事件 | 返回同一个状态引用 |

插件不写自己的事件类型：会话日志的读路径只认宿主那份已知类型清单，而日志的追加入口设不了「可忽略」标记——自建类型写出的日志之后打不开。状态因此只由上面这几种已有事件推导。

调用记录是**映射而不是单槽**：宿主可能并行派发工具调用，单槽会让先完成的那个结果配到后一个调用的入参上——前者被丢弃、后者被冒充。映射让每个调用与自己的结果配对，最后成功的那个胜出。

入参解析失败（日志被截断、内容损坏）时不报错也不递增修订号，只删掉这条记录：折叠函数必须对任何输入都能返回一个状态。

### 有效状态与已提交状态

两个读法，不能混用：

| 读法 | 含义 | 谁用 |
| --- | --- | --- |
| 有效状态 | 「正在执行的那次选择」优先，没有则用已提交状态 | 提示词段落、工具执行——问「这一刻算不算在模式里」 |
| 已提交状态 | 只看已提交那一项 | 进入命令的处理函数——问「这条命令进来之前是什么状态」 |

命令记录在处理器之前入日志：先追加开始、再调处理函数、最后追加结束。所以处理函数执行期间，「正在执行的那次选择」已经是本次的选择，「已提交状态」还是旧值。

## 生命周期绑定

| 时机 | 做什么 | 什么条件下 |
| --- | --- | --- |
| 每次装配系统提示词 | 求值 `method:policy` 段落的文本 | 该会话有效状态为真才给协议文本，否则给空串 |
| 每次执行 `plan_submit` | 两道路径校验 + 落盘 + 回显 | 见「工具执行顺序」 |
| 进入命令 | 注入一行提示，告知协议已生效 | 仅裸 `/method`（无参） |

- 投影不自己订阅会话事件：注册之后由框架驱动折叠，没有需要清理的订阅。
- 其余注册（工具、提示词段落、命令、可选服务注入）都挂在插件自己的生命周期上，卸载即回收。

## 提示词注入

方法协议走系统提示词段落，不走消息注入：

| 项 | 取值 |
| --- | --- |
| 段落名 | `method:policy` |
| 排序位置 | 取计划模式策略段（`PLAN_POLICY`）的位置 |
| 未激活时 | 渲染空串，宿主丢弃空段落——不激活就零 token |
| 段落文本 | 每次装配时求值的提供者，不是快照，进出模式立即生效 |
| 提供者抛异常 | 贡献空串（抛出去会让整个装配失败） |
| 文本长度 | 约 980 字符 |

段落内容是六条必答项（目标与非目标、约束、方案比较、步骤、每步完成判定、整体验证）加提交与执行的约定，全部领域中立，不含编程词汇。

## 计划参数 schema

`plan_submit` 的参数是标准 JSON Schema，**不是** `defineTool` 那套 DSL。

| 项 | 内容 |
| --- | --- |
| 顶层 | `{ plan: {...} }`，`additionalProperties: false`，`required: ["plan"]` |
| 必填性写法 | 每个对象自己的 `required` 字符串数组 |
| 模型可见 | schema 里每个字段的 `description` 就是规格说明，模型照它填 |

schema 用标准写法而不是 DSL，因为 `ctx.tools.register` 原样透传 `parameters`，只有 `defineTool` 会接 DSL 并顺带跑校验。

## 两层校验

| 层 | 拦什么 | 在哪执行 | 失败表现 |
| --- | --- | --- | --- |
| 参数形状 | 缺字段、类型错、枚举非法、**多余或拼错的字段** | `execute` 开头，调宿主的 `validateJsonSchemaValue` | 工具报错，逐条列出违规路径 |
| 内容语义 | 空串、条目不够、完成判定不可观察、依赖成环、验证没覆盖、可逆性非布尔、置信度非法 | `validate.js` 的 `validatePlan` | 工具报错，格式 `<路径>: <规则>` |

第一层必须自己调：注册时只校验输出 schema，`parameters` 只透传，`execute` 拿到的是裸入参。不自己调的话 `additionalProperties: false` 只是装饰——拼错字段名的计划会被静默接受，因为内容校验器只读它认识的字段。

校验器从宿主安装目录解析：`@deepseek-ai/dsh-tools` 不是 profile 的依赖，普通动态 import 拿不到。解析顺序是裸包名 → 从 `process.argv[1]` 往上找 `<目录>/node_modules/@deepseek-ai/dsh-tools/lib/index.js` 与 `<目录>/@deepseek-ai/dsh-tools/lib/index.js`。全部失败时跳过第一层、只跑第二层，插件照常加载。

## 内容校验规则

阈值是代码常量：

| 常量 | 值 | 约束谁 |
| --- | --- | --- |
| `MIN_TASKS` | 2 | 至少两个任务 |
| `MIN_ALTERNATIVES` | 2 | 至少两个方案候选 |
| `MIN_ASSUMPTIONS` | 1 | 每个任务至少一条失败原因 |
| `MAX_FIELD_CHARS` | 400 | 单行字段（标题、名称、id 等） |
| `MAX_BLOCK_CHARS` | 4000 | 多行字段（目标陈述、优点、代价、理由、完成判定、验证内容） |

逐项规则：

| 字段 | 必填 | 额外约束 |
| --- | --- | --- |
| `goal.statement` | 是 | 非空 |
| `goal.nonGoals` | 是 | 至少 1 条，互相不重复 |
| `constraints[].text` | 是 | 互相不重复 |
| `constraints[].kind` | 是 | `hard` 或 `soft` |
| `alternatives.options[]` | 是 | 至少 2 个，名称互不重复 |
| `alternatives.options[].pros/cons` | 是 | 非空 |
| `alternatives.chosen` | 是 | 必须与某个候选名称完全一致（忽略大小写）；归一成候选里的原始写法 |
| `alternatives.reason` | 是 | 非空 |
| `tasks[].id` | 是 | 匹配 `[a-z0-9][a-z0-9-]*`，全计划唯一 |
| `tasks[].status` | 是 | `pending` / `in_progress` / `completed` / `skipped` |
| `tasks[].dependsOn` | 是 | 可为空数组；每项必须指向存在的任务，不许指向自己，整图不许成环 |
| `tasks[].assumeReasons` | 是 | 至少 1 条，互相不重复 |
| `tasks[].doneWhen` | 是 | 必须可观察，见下 |
| `tasks[].artifacts` | 是 | 可为空数组；互相不重复 |
| `verification[].task` | 是 | 任务 id 或 `*` |
| `verification[].check` | 是 | 必须可观察，判据同 `doneWhen` |
| `verification[].expected` | 是 | 非空 |
| `verification` 整体 | 是 | 每个任务都被覆盖，或存在一条 `task: "*"` |
| `reversible` | 是 | 布尔 |
| `confidence` | 是 | `high` / `medium` / `low` |

重复判定忽略大小写与多余空白：`不改 CI` 与 `不改 ci` 算同一条。重复是凑够最小条数最省事的办法，不拦掉的话最小值形同虚设。

依赖成环用三色深度优先搜索检测，报错带完整环路。

## 可观察判定的判据

`doneWhen` 与 `verification[].check` 共用同一套判定。只要命中下列任意一类就放行：

| 类型 | 判据 | 例子 |
| --- | --- | --- |
| 代码片段 | 反引号里有实质内容：至少两个字符，且汉字数不超过总长一半 | `` `pnpm test` `` |
| 命令名 | 命中白名单：npm / pnpm / yarn / npx / git / curl / wget / bash / zsh / python3 / pytest / vitest / jest / cargo / docker / kubectl / terraform / ansible / gradle / maven / msbuild | `跑 pnpm test` |
| 本地路径 | 带分隔符与扩展名尾巴 | `report/q3.docx 已生成` |
| 裸文件名 | 已知扩展名 | `README.md 已更新` |
| 比较 | 运算符后跟操作数，或「X 为 Y」 | `覆盖率 ≥ 80%`、`accepted 为 true` |
| 数量带单位 | 数字加页/条/行/个/份/元/%/天等 | `输出 42 行` |
| 引号里的值 | 引号内容非中文散文，或任意数字/版本号 | `「订单号 ABC123」` |
| 产物名词 | 邮件 / 回执 / 合同 / 订单 / 报告 / 清单 / 签字 / 截图 / 凭证 等 | `收到订票确认邮件` |
| 状态达成 | 已生成 / 已收到 / 存在 / 已通过 / 能打开 / 已完成 / 通过…测试 等 | `合同已签署` |

九类全不命中才拒绝。URL 在做路径与比较判定前先剥掉：链接指向别处，不是执行者能查的产物；同时避免 URL 里的 `=`、`>`、协议斜杠满足比较或路径规则。

判断方向是「能不能看见」，不是「像不像代码」：旅行计划的「收到订票确认邮件」与报告计划的「收到三位评审人的书面意见」同样成立。

## 工具执行顺序

| 顺序 | 条件 | 动作 |
| --- | --- | --- |
| 1 | 参数不满足 schema | 抛错，逐条列出违规（最多 12 条） |
| 2 | 调用没有关联代理 | 抛错 |
| 3 | 该会话有效状态为假 | 抛错，提示先运行 `/method` |
| 4 | 内容校验抛 `PlanError` | 抛错，文案是「计划被拒绝 — `<路径>: <规则>`」，末尾要求改正后重新提交完整计划 |
| 5 | 其余 | 预留修订号、渲染文本、落盘、修订号大于 1 时注入一行提示、返回结果 |

- 修订号在 `execute` 里同步预留，不等结果折叠：两个并行调用会读到同一个已提交值，共用同一个修订号，然后写同一个文件互相覆盖。进程内按会话记一个预留计数器，取「已提交值」与「计数器」的较大者加一。
- 落盘失败（目录不可写、磁盘满）抛错并带出目标路径，不返回成功。
- 输出是 `accepted`、`revision`、`planPath`、`taskCount`、`rendered` 五项；渲染函数把它们拼成「已接受 + 落盘位置 + 计划全文」。

## 计划路径解析

- 计划路径 = 从会话工作目录往上找到的最近一个带 `.git` 的目录，其下的 `.method/plan.md`；一路找不到这样的目录就用工作目录本身。
- 这套找法跟宿主的指令文件读取机制一致（默认的项目标记只看版本库目录，找不到就用会话工作目录）。
- **用户主目录不算锚点**：主目录下有 `~/.git`（dotfiles 仓库）很常见，不排除的话所有项目的计划都会落到 `~/.method/plan.md`，跑到项目外面且互不区分。
- 会话工作目录取宿主的 `workingDirectory` 投影，不是会话头里的创建时目录：用户中途 `cd` 之后，计划要落到新目录。
- 投影缺席时依次退回会话头里的工作目录、宿主进程的当前目录。
- 计划目录由插件用 `mkdirSync` 递归创建，失败留到写计划文件时以工具错误暴露。

## 落盘与自忽略

| 动作 | 内容 |
| --- | --- |
| 写计划 | 渲染后的全文加换行，UTF-8 |
| 写忽略文件 | 同目录下 `.gitignore` 不存在时写入一行 `*` |

- `.method/` 落在用户项目里，`git status` 因此会多出目录。自写忽略文件让它整目录不进版本控制，同时**不动用户根目录的 `.gitignore`**——那是用户自己该审的改动。
- 计划是文档不是中间产物：每次成功提交覆盖前一份，修订号递增。

## 渲染格式

`renderPlan` 产出的文本由固定小节组成，顺序如下：

| 小节 | 内容 |
| --- | --- |
| 标题 | `# 执行计划 revision <n>` |
| 目标 | 目标陈述 |
| 不做（非目标） | 逐条列出 |
| 约束 | `[hard]` / `[soft]` 加内容 |
| 方案比较 | 每个候选列优点与代价，已选的标 `**（已选）**`，末尾一行选择理由 |
| 任务 | 编号、状态、标题、id、依赖、失败原因、完成判定、产出 |
| 验证 | `[任务id或 *]` 加检查内容与期望 |
| 可逆 / 置信度 | 两行 |
| 执行契约 | 三条固定要求：按序执行且改计划须重提、每步做完立刻验证且不通过就停、全部完成后逐条运行验证并贴实际输出 |

执行契约是固定文本，不进 schema：模型每步之后重读的是这段渲染结果，所以它必须自带约束，而不是只回一句「已收到」。

## 命令实现

命令通过可选服务注入注册（该服务缺席时插件仍能激活，只是进不去模式）。处理器顺序：

| 顺序 | 条件 | 动作 |
| --- | --- | --- |
| 1 | 参数是 `off`、已提交状态为假 | 回「未开启」，别的都不做 |
| 2 | 参数是 `off`、已提交状态为真 | 注入一行提示（计划仍在盘上但不再强制），回执说明已关闭 |
| 3 | 不是 `off`、已提交状态为假、计划模式活跃 | 回错误，状态不变 |
| 4 | 不是 `off`、无参数 | 注入一行提示（协议已生效），回执说明直接说要做的事 |
| 5 | 不是 `off`、有参数 | 把参数作为这一轮的用户消息提交，回执说明模式已开 |

状态一律由命令开始与命令结束这两条会话事件承载，处理函数自己不写任何状态。

## 设计约束

| 约束 | 内容 |
| --- | --- |
| 状态由会话日志推导 | 插件不写自己的事件类型 |
| 状态必须是无损 JSON | 投影缓存拒收 Map、Set、undefined；待提交记录是普通对象 |
| 零宿主包依赖 | 只 import 仓库内的模块与 Node 自带模块；参数形状校验从宿主安装目录运行期解析 |
| 提示词段落给空串而不是抛错 | 提供者抛异常会毁掉整个装配 |
| 计划参数 schema 手写 | 注册时只校验输出 schema，参数 schema 直接透给模型 |
| 结构性问题用代码拦，内容质量靠提示词 | 计划是否想清楚无法机器判定，校验只管能判的那部分 |

## 宿主接口面

全部是运行期从上下文、代理、会话上取的实例成员，没有 import：

| 来源 | 用到什么 |
| --- | --- |
| 投影服务 | 注册投影单元、按会话取状态（`method` 与 `workingDirectory` 两个键） |
| 提示词服务 | 注册段落、取计划模式策略段的排序位置 |
| 命令服务 | 注册命令（标识、名字、描述、输入提示、处理函数） |
| 工具服务 | 注册工具 |
| 可选服务 | 注入命令服务、取计划模式状态 |
| 代理 | 会话、注入消息、转向提交 |
| 会话 | 会话头里的工作目录 |
| 工具执行记录 | 关联代理、入参 |
| 宿主安装目录 | 运行期解析 `validateJsonSchemaValue` |

- 必需注入是工具、系统提示词、会话投影三项；命令与计划模式都是运行期可选，缺席时插件仍能激活。
- 宿主升级后这些签名可能变动，核对时跑 docs/交接文档.md 的「验证清单」。

## 已知边界

- 不阻止模型跳过计划直接干活：`plan_submit` 只在模式里可用，但没有守卫拦写操作。
- 可观察判定靠词表与结构：同一意思换措辞可能一边被拒一边通过（`酒店订好了` 被拒，`已完成酒店预订` 通过）。
- 参数形状校验依赖宿主安装目录可解析；解析失败时只剩内容校验，拼错字段名会被静默接受。
- 计划路径按工作目录定位，不含会话标识：同一项目两个并行会话写同一份 `plan.md`。
- 计划模式互斥是单向的：本插件知道计划模式，反过来不知道。
